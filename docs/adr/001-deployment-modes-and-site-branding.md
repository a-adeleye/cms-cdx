# ADR 001: Deployment modes and site branding

Status: accepted (2026-07-17)

## Context

The CMS manages multiple sites. Some sites are entirely generated by the CMS, while others already have a landing page in a Git repository and need the CMS to own only a nested blog such as `/blog`. Treating both cases as a full-directory upload would overwrite the existing landing site.

## Decision

Each site stores independent preview and production deployment configurations. Supported modes are:

- `none`: generate and retain the static output locally without an external provider call.
- `cloudflare_pages`: upload the full generated site to a Cloudflare Pages Direct Upload project.
- `firebase`: upload the full generated site to Firebase Hosting (live or preview channel).
- `git_repository`: clone a configured HTTPS repository and branch from the server's Git host allowlist (GitHub and GitLab by default), replace only `contentPath` with the generated `blogPath` subtree, commit, and push without force.

Repository credentials are environment-variable references. Tokens are never stored in the database or embedded in repository URLs. Repository paths are canonicalized and confined to the checkout, `.git` cannot be targeted, and production accepts only allowlisted HTTPS hosts.

Every build row is inserted before generation or deployment begins. Success, failure, provider URL, log, and Git revision are written back to that row, so failed external operations remain visible in history. Preview output is isolated by site slug.

Site branding is persisted as references to site-owned media assets (`logo_media_id` and `favicon_media_id`). The generator resolves their public URLs and renders the logo, favicon, and site description. Templates shown in the admin catalogue are rendered by the same production rendering code; arbitrary database-only template registration is not supported.

## Consequences

- A landing-page repository keeps every file outside the configured CMS-owned blog directory.
- Preview and production may use different providers, repositories, or branches.
- A full-site provider receives the root index, blog subtree, sitemap, RSS, and robots files; a repository provider receives only the blog subtree.
- Git-integrated hosts such as Cloudflare Pages deploy after the CMS pushes the configured branch. The CMS records the pushed revision, not the downstream host's completion status.
- Public media delivery remains an operator responsibility: `S3_PUBLIC_URL` must point to a browser-readable bucket or CDN.
